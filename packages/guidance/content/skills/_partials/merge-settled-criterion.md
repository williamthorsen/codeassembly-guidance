**Merge-settled criterion convention:** When writing a ticket whose work is a code change, state only the criteria that its pull request can satisfy or falsify. The test is whether the pull request's tests, checks, or review can show the criterion to hold or to fail at merge. A criterion that fails the test is an operational step, which depends on elapsed time, on deployed state, or on a run against shared data, such as "a deployed agent, run a day after seeding, places every fixture in its expected section". Move such a step to the ticket that consumes the change, or propose a ticket of its own for it when the tracker does not contain one that consumes the change, so that the code ticket can close when its pull request merges.
